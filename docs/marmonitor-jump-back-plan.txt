marmonitor jump-back 설계안

목적
- marmonitor jump 후에 "원래 보던 자리"로 빠르게 돌아가는 기능의 기준을 명확히 한다.
- 구현 전에 `back`의 의미를 고정해서, stack / origin / 탭 / client 개념이 섞이지 않게 한다.
- 현재 기준은 `simple-made-easy-global-merged-v3.3.md`의 관점에 맞춘다.
  - 구현 세부보다 먼저, 개념 경계를 분명히 한다.

문제 정의
- 사용자는 marmonitor로 attention 항목이나 특정 세션으로 점프할 수 있다.
- 점프 자체는 유용하지만, 여러 터미널 탭과 tmux client를 병행해서 쓸 때
  "어디로 돌아가야 하는가"의 의미가 모호해질 수 있다.
- 이 기능은 "직전 위치 stack"이 아니라 "이 화면에서 처음 점프하기 전 자리"로 정의하는 편이 더 자연스럽다.

최종 정의
- 베이스(base) = 현재 tmux client에서 anchor가 비어 있을 때, 첫 jump 직전의 위치
- `jump-back` = 항상 그 베이스로 복귀
- 복귀가 성공하면 anchor를 clear

사용자 관점 설명
- "이 화면에서 처음 점프하기 전 자리로 돌아간다"
- 여러 번 jump해도 back은 직전 단계로 한 칸씩 되돌아가는 것이 아니라,
  jump 세션이 시작되기 전의 원래 자리로 돌아간다.

왜 stack이 아닌가
- stack 모델은 `A -> B -> C -> back = B`가 된다.
- 현재 원하는 동작은 `A -> B -> C -> back = A`에 가깝다.
- 따라서 1차 구현은 history stack보다 단일 origin anchor가 더 적합하다.

내부 구현 모델
- 사용자 개념은 "첫 jump 전 자리"
- 내부 모델은 `client-scoped anchor`
- 즉, 구현은 tmux client별로 anchor를 하나 저장하지만,
  사용자에게는 "이 화면의 원래 자리"로 설명한다.

데이터 구조
- 저장 단위: tmux client별 단일 anchor
- 저장 키: `client_id`가 있으면 그 값을 쓰고, 비어 있으면 `client_tty`를 key로 쓴다.
- 저장 위치:
  - 우선안: `TMPDIR/marmonitor/jump-anchors/<clientId>.json`
- 저장 필드:
  - `clientId`
  - `clientTty`
  - `originSessionId`
  - `originWindowId`
  - `originPaneId`
  - `recordedAt`
  - `lastJumpedAt`

예시
{
  "$3": {
    "clientId": "$3",
    "clientTty": "/dev/ttys017",
    "originSessionId": "$1",
    "originWindowId": "@41",
    "originPaneId": "%118",
    "recordedAt": 1775010500000,
    "lastJumpedAt": 1775010520000
  }
}

왜 client_id를 기준으로 삼는가
- tmux 내부 식별자로 직접적이다.
- 터미널 앱의 "탭" 개념은 앱마다 다르지만, tmux client는 우리가 실제로 제어 가능한 단위다.
- 다만 실제 tmux 버전에 따라 `client_id`가 비어 있을 수 있으므로, 구현은 `client_tty` fallback을 반드시 둔다.

기록 규칙
1. jump를 실제로 실행하기 직전, anchor가 없을 때만 기록
2. 이미 anchor가 있으면 덮어쓰지 않음
3. marmonitor가 주도하는 jump만 기록
4. 사용자의 수동 tmux 이동은 기록하지 않음

기록 대상
- click jump
- direct jump
- attention jump
- popup에서 선택한 jump
- `jump --pid`
- `jump --attention-index`

기록하지 않는 대상
- 일반 statusline render
- attention / jump 목록 조회만 하는 동작
- 사용자의 일반 tmux 이동

의미 예시
- A에서 시작
- B로 jump -> anchor=A 기록
- C로 jump -> anchor=A 유지
- D로 jump -> anchor=A 유지
- jump-back -> A로 복귀

clear 규칙
- 아래 경우에 anchor를 clear한다.

1. jump-back 성공
- pane / window / session 어느 수준이든 유효한 복귀가 완료되면 clear

2. origin이 완전히 사라진 것이 확인됨
- pane 없음
- window 없음
- session 없음
- 이 경우 더 이상 복귀할 원본이 없으므로 clear

3. 명시적 clear / reset
- 사용자가 anchor를 버리겠다고 명시한 경우

4. stale cleanup
- client가 더 이상 존재하지 않거나
- anchor가 너무 오래된 경우

실패 시 규칙
- tmux command 자체가 일시적으로 실패한 경우에는 clear하지 않음
- 이유:
  - 일시적 실패일 수 있고
  - retry 가치가 있기 때문

복귀 우선순위
1. `originPane`
2. `originWindow`
3. `originSession`

설명
- pane이 남아 있으면 가장 정확하게 원래 자리로 돌아간다.
- pane이 없어도 window가 있으면 최소한 같은 작업 맥락으로 복귀할 수 있다.
- window도 없어도 session이 있으면 그 범위까지는 복구한다.

수동 이동에 대한 정책
- 1차 구현에서는 수동 이동을 감지하거나 anchor를 재해석하지 않는다.
- 즉, 첫 jump 이후 사용자가 수동으로 pane/window를 바꿔도,
  `jump-back`은 여전히 최초 anchor로 돌아간다.

왜 이렇게 단순화하는가
- 규칙이 예측 가능하다.
- 수동 이동 감지는 구현 복잡도에 비해 신뢰성이 낮다.
- 1차 목표는 "원래 하던 자리로 돌아가기"를 단순하게 구현하는 것이다.

필수 명령
1. `jump-back`
- 현재 client의 anchor가 있으면 원래 자리로 복귀

선택 명령
1. `jump-anchor-clear`
- 현재 client의 anchor를 지움
- 다음 jump에서 새 anchor가 자동으로 잡히게 함

2. `jump-anchor-set`
- 지금 위치를 새 anchor로 강제 설정
- 1차 필수는 아님

추천 UX
- 1차는 `jump-back`만 구현
- 이후 필요하면 `jump-anchor-clear` 추가
- history browser나 stack 모드는 1차 범위에서 제외

왜 1차에 reset을 강제하지 않는가
- 기본 모델만으로도 대부분 해결된다.
- back 후 clear되므로, 일반적인 사용 흐름에서는 따로 reset할 일이 많지 않다.

stale cleanup 정책
- 기본 cleanup 조건:
  - tmux client list에 현재 `client_id`가 없음
  - 또는 마지막 jump 기준 age(`lastJumpedAt ?? recordedAt`)가 24시간 초과
- cleanup 타이밍:
  - jump 실행 전
  - jump-back 실행 전
  - 또는 별도 housekeeping 함수

edge case
1. 같은 client에서 연속 jump
- 첫 jump 이전 위치만 anchor로 유지

2. origin pane이 닫힘
- window -> session 순으로 fallback

3. origin session도 삭제됨
- 복귀 실패로 보고 anchor clear

4. 다른 탭/다른 client에서 jump
- 각 client anchor는 서로 독립

5. popup 안에서 jump
- popup 호출에 사용된 `targetClient`를 그대로 계승

6. anchor가 없는 상태에서 jump-back
- tmux에서는 조용한 no-op이 적절
- CLI 직접 실행 시에는 짧은 메시지를 줄 수 있음

1차 구현 범위
1. client별 anchor file 저장
2. jump 직전 anchor 없으면 현재 위치 저장
3. `jump-back`
4. 복귀 성공 시 clear
5. pane -> window -> session fallback
6. 최소한의 stale cleanup

1차 범위에서 제외
- multi-step stack/history
- visual anchor indicator
- 수동 이동 감지
- 자동 복귀
- 전역 shared "last location"

파일 경계 제안
- `src/tmux/jump-anchor.ts`
  - anchor read/write/clear
  - stale cleanup
- `src/tmux/navigation.ts`
  - jump 직전 최초 anchor 기록
  - jump-back orchestration
- `src/tmux/index.ts`
  - 현재 위치 조회
  - jump-back command builder
  - pane/window/session fallback
- `src/cli.ts`
  - `jump-back` 서브커맨드 진입점
- `tests/tmux.test.mjs`
  - fallback 규칙 테스트
- `tests/status-click.test.mjs`
  - click jump가 anchor를 남기는지 확인

테스트 시나리오
1. 첫 jump 전에 anchor 생성
2. 연속 jump 시 anchor 유지
3. jump-back 시 origin pane 복귀
4. pane missing -> window fallback
5. window missing -> session fallback
6. origin 모두 missing -> clear
7. 다른 client anchor와 충돌하지 않음
8. anchor 없는 jump-back은 no-op

최종 판단
- 1차는 stack보다 단일 anchor가 더 적합하다.
- 사용자 개념은 "첫 jump 전 자리"
- 구현 개념은 "client별 단일 anchor"
- 이 둘을 분리해서 설명하면 기능 의미와 구현 책임이 모두 단순해진다.

현재 구현 상태
- 구현 완료
  - `jump-back` CLI 추가
  - click jump / direct jump / interactive jump가 최초 anchor를 기록
  - `pane -> window -> session` fallback으로 복귀
  - 성공 시 anchor clear
  - stale cleanup 추가
  - anchor payload는 복귀에 필요한 origin 식별자와 stale cleanup용 시간 정보만 유지
- 실제 tmux 확인
  - 실제 tmux 환경에서 `client_tty` 기준 anchor 생성
  - `jump-back` 실행 성공
  - 성공 후 anchor clear 확인
- 로컬 사용 바인딩
  - `~/.tmux.conf`
  - `bind-key -n M-b run-shell -b "marmonitor jump-back --client-tty #{client_tty} >/dev/null 2>&1"`
