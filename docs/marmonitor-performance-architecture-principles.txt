marmonitor 성능 아키텍처 원칙

목적
- marmonitor는 단순한 CLI가 아니라, 상태줄, summary popup, jump, jump-back, collector, 진단 명령이 함께 있는 상호작용형 도구다.
- 이 제품의 성능 문제는 보통 "한 함수가 느리다"보다 "서로 다른 종류의 일이 같은 경로에 섞인다"는 형태로 나타난다.
- 이 문서는 앞으로 기능이 늘어나도 상태줄 지연, 클릭 반응 저하, 경계 붕괴가 반복되지 않도록 하기 위한 전역 원칙을 정리한다.
- 이 문서는 `Simple Made Easy v3.2`의 질문, 즉 "독립적이어야 할 것들이 분리 불가능하게 엮여 있는가"를 marmonitor의 제품 맥락과 코드 작성 판단에 맞게 번역한 것이다.

Simple Made Easy와의 연결
- marmonitor에서 단순함은 기능 수가 적다는 뜻이 아니다.
- 단순함은 서로 다른 이유로 존재하는 것을 분리하고, 같은 이유로 존재하는 것을 한 경계 안에 두는 것이다.
- 편한 위치에 코드를 더하는 것은 용이함일 수는 있어도, 단순함은 아니다.
- 특히 이 제품에서는 상태줄, popup, jump, collector, client 고유 상태가 가장 쉽게 서로를 오염시킨다.

핵심 원칙
- 실시간 경로는 얇게 유지한다.
- 원본 상태와 파생 상태를 구분한다.
- 해석은 공유하고, 표현은 그 위에 얹는다.
- 공용 상태와 client 고유 상태를 섞지 않는다.
- benchmark는 원칙 자체가 아니라, 원칙이 지켜졌는지 검증하는 수단으로 사용한다.

1. 성능 계약

실시간 경로
- 예:
  - 상태줄 출력
  - 상태줄 클릭 반응
  - jump-back 가능 여부 표시
  - 번호 기반 빠른 jump
- 기대:
  - 사용자는 즉시 반응을 기대한다.
- 허용:
  - 이미 준비된 결과를 읽는 것
  - 작은 범위의 결정적 조합
  - client 고유 표시를 마지막에 얹는 것
- 피해야 할 것:
  - 새로운 관찰
  - 넓은 재해석
  - 전체 목록 재정렬이나 재집계

준실시간 경로
- 예:
  - summary popup
  - attention 목록
  - jump 대상 선택 UI
- 기대:
  - 짧은 지연은 허용되지만, 사용자가 흐름을 잃을 정도로 무거우면 안 된다.
- 허용:
  - 공용 상태를 기준으로 한 정렬, 필터, 묶기
  - 이미 있는 해석 결과를 다른 관점으로 펼치는 것
- 피해야 할 것:
  - 원천 수집을 다시 시작하는 것
  - 표면마다 독립된 해석 체계를 만드는 것

비실시간 경로
- 예:
  - 전체 스캔
  - 상세 진단
  - 디버그성 확인
  - 재색인, 복구, 청소
- 기대:
  - 느릴 수 있다. 대신 느린 이유와 경계가 명확해야 한다.
- 허용:
  - 비용 큰 계산
  - 복구성 작업
  - 상세 분석

의미
- 새 기능을 논의할 때는 먼저 "무엇을 보여줄까"보다 "어느 경로에서 비용을 낼 것인가"를 정해야 한다.
- 이 분류가 흐려지면 작은 기능도 상태줄을 무겁게 만든다.

2. 상태의 층위

원본 상태
- 외부 세계를 관찰한 결과다.
- 세션 집합, 현재 활동, 현재 phase, 현재 매칭 결과처럼 제품이 신뢰해야 하는 입력이 여기에 속한다.
- 이 층은 권위 원본이어야 한다.

파생 상태
- 원본 상태를 제품에서 의미 있는 형태로 바꾼 결과다.
- 예:
  - agent별 개수
  - 문제 세션 개수
  - 우선순위가 매겨진 attention 목록
  - jump 후보
  - summary popup 대상 목록
- 핵심:
  - 같은 파생 결과는 여러 표면이 공유해야 한다.
  - 같은 의미를 상태줄, popup, jump가 각자 따로 다시 계산하면 안 된다.

표현 결과
- 사용자가 실제로 보는 최종 형식이다.
- 예:
  - 상태줄 문자열
  - popup 텍스트
  - 클릭 가능한 표면
  - 배지, 번호, 아이콘
- 표현은 파생 상태를 보여주는 방식이다.
- 표현 단계에서 포맷팅과 얕은 조합은 가능하지만, 제품 의미를 새로 해석하기 시작하면 경계가 무너진다.

의미
- 성능을 유지하려면 원본을 여러 번 읽지 않아야 하고, 같은 파생 계산을 여러 번 하지 않아야 한다.
- 기능 확장의 기본 단위는 화면이 아니라 공유 가능한 파생 의미여야 한다.

3. 공용 상태와 client 고유 상태

공용 상태
- 모든 표면이 함께 써도 되는 상태다.
- 예:
  - 현재 세션 집합
  - 공용 요약 수치
  - 공용 attention 정렬

client 고유 상태
- 특정 화면이나 현재 문맥에서만 의미가 있는 상태다.
- 예:
  - jump-back 가능 여부
  - 현재 화면의 복귀 기준점
  - 클릭이 일어난 client 문맥

원칙
- 공용 상태는 공용 경로에서 계산하고 재사용한다.
- client 고유 상태는 가능한 마지막 단계에서 결합한다.
- 공용 결과가 client 상태를 품기 시작하면, 한 화면의 문맥이 다른 화면의 출력과 캐시를 오염시킨다.

의미
- collector는 공용 상태를 다루는 쪽에 가깝고, 필요하다면 실시간 경로에서 직접 만들면 안 되는 공용 파생 결과까지 함께 공급할 수 있다.
- jump-back, 현재 문맥 표시, 클릭 대상 해석은 client 고유 상태에 가깝다.
- 둘이 같은 산출물이나 같은 책임으로 합쳐지기 시작하면 복잡성이 급격히 커진다.

4. marmonitor 기능을 어디에 놓아야 하는가

상태줄
- 적합:
  - 이미 계산된 요약값
  - 이미 정해진 attention 결과의 상위 일부
  - client 문맥에 따른 아주 얕은 표시
- 부적합:
  - 새 정렬 규칙
  - 넓은 재분류
  - popup에서만 쓸 자세한 정보 준비
  - "혹시 필요할지 모른다"는 이유로 붙는 계산

summary popup
- 적합:
  - 공용 해석 결과를 다른 관점으로 펼쳐 보여주는 것
  - 특정 badge가 의미하는 대상 목록
  - 클릭 이후에만 필요한 부가 정보
- 부적합:
  - popup마다 독자적인 해석 규칙을 갖는 것
  - 상태줄과 다른 기준의 요약을 새로 만드는 것
  - popup을 열 때마다 원천 수집을 다시 시작하는 것

jump / jump-back
- 적합:
  - 현재 문맥에서의 빠른 이동
  - 선택된 공용 후보에 대한 즉시 실행
  - client 고유 상태를 이용한 복귀
- 부적합:
  - 광범위한 검색
  - 전체 상태 재평가
  - 공용 상태를 client별로 다시 재해석하는 것

의미
- jump는 주로 공용으로 준비된 후보를 소비하는 행동에 가깝다.
- jump-back은 client 고유 anchor 상태를 소비하는 복귀 행동에 가깝다.
- 둘을 같은 이동 기능으로 볼 수는 있지만, 의존하는 상태의 성격은 다르다.

collector
- 적합:
  - 공용으로 재사용되는 현재 상태
  - 여러 표면이 함께 쓰는 파생값의 원재료
  - 실시간 경로에서 다시 계산하면 안 되는 공용 결과
- 부적합:
  - client별 표시
  - 클릭 문맥
  - 현재 화면에만 의미가 있는 상태
  - 사용자 입력 직후의 일회성 행동

5. 코드 작성 원칙으로 번역하면

좋은 변경
- 변경 이유가 하나인 경계 안에서 끝난다.
- 원본, 파생, 표현 중 무엇을 건드리는지 설명할 수 있다.
- 기존 파생 결과를 재사용한다.
- 공용 상태와 client 상태를 분리한다.
- 실시간 경로를 더 똑똑하게 만드는 대신, 더 얇게 유지한다.

경계가 무너지는 징후
- 한 함수가 상태를 읽고, 정렬하고, 포맷팅하고, 클릭 동작까지 함께 다룬다.
- popup 하나를 바꾸는데 상태줄 설명도 같이 필요하다.
- 같은 의미를 서로 다른 경로가 조금씩 다르게 정렬한다.
- 캐시를 붙일수록 안심되기보다 구조가 더 의심스러워진다.

실무용 세 문장
- 새 기능을 시작하기 전에 아래 세 문장을 쓸 수 있어야 한다.
  - 이 기능의 원본은 무엇인가
  - 이 기능의 파생값은 무엇인가
  - 이 기능은 어느 경로에서 비용을 내야 하는가
- 이 세 문장이 모호하면, 아직 구현을 시작할 단계가 아니다.

예외를 다루는 기준
- 작은 예외 자체를 금지할 필요는 없다.
- 다만 그 예외가 새로운 관찰을 실시간 경로로 끌어오거나, 공용 상태와 client 고유 상태의 경계를 흐리기 시작하면 안 된다.
- 예외가 필요하다면 "왜 이 예외가 경계를 깨지 않는가"를 먼저 설명할 수 있어야 한다.

6. benchmark와 수치의 역할

원칙
- benchmark는 성능 원칙을 대신하지 않는다.
- benchmark는 이미 정한 경계와 성능 계약이 지켜졌는지 확인하는 수단이다.
- 최적화는 "이론적으로 빨라 보인다"가 아니라, 목표 경로의 수치가 실제로 좋아질 때만 유지한다.

좋은 사용법
- 같은 경로를 전후 비교한다.
- 실시간, 준실시간, 비실시간 수치를 섞지 않는다.
- 평균만 보지 않고 최악값과 분포를 함께 본다.
- 사용자가 실제로 체감하는 경로를 기준점으로 삼는다.

최적화 반영 기준
- 최적화를 시작하기 전에 먼저 아래 세 가지를 적는다.
  - 무엇을 빠르게 만들려는가
  - 어떤 benchmark로 그 경로를 검증할 것인가
  - 어떤 수준의 개선이 나오면 유지할 것인가
- 이 세 가지가 없으면, 그 변경은 최적화가 아니라 추측에 가깝다.
- benchmark 결과가 목표 경로에서 의미 있는 개선을 보여주지 못하면, 구현이 그럴듯해 보여도 유지하지 않는다.
- 한 경로를 빠르게 만드는 대신 더 중요한 경로를 느리게 만들면, 그 최적화는 실패다.
- 실시간 경로 최적화는 특히 다음 순서를 따른다.
  - 먼저 가장 체감이 큰 경로를 고른다.
  - 그 경로를 기준으로 전후 수치를 잰다.
  - 개선이 없거나 분산만 커지면 되돌린다.

의미
- 이 제품에서 억지 최적화는 대개 작은 helper, 캐시, 분기를 늘리지만 사용자 체감은 바꾸지 않는다.
- 따라서 성능 변경은 "복잡도 증가"와 "측정된 이득"이 함께 있을 때만 정당화된다.

주의
- popup 최적화를 했는데 상태줄 숫자만 보고 결론 내리면 안 된다.
- cold path와 warm path를 섞어 평균만 보면 실제 체감과 멀어진다.
- 수치가 좋다는 이유만으로 경계 위반을 정당화하면 안 된다.

7. 기능이 계속 늘어날 때 특히 조심할 것

상태줄이 작은 대시보드가 되는 것
- 상태줄은 압축된 결과를 빠르게 보여주는 곳이다.
- 설명적 기능이 계속 들어가면 가장 먼저 무너진다.

popup이 별도 제품처럼 커지는 것
- popup은 상태줄의 의미를 풀어주는 역할이어야 한다.
- 독자적인 해석 체계를 갖기 시작하면 같은 데이터를 두 번 운영하게 된다.

jump가 탐색 시스템이 되는 것
- jump는 빠른 이동이어야 한다.
- 검색, 진단, 해석까지 떠안으면 경계가 흐려진다.

client별 기능이 공용 상태를 오염시키는 것
- jump-back, 현재 문맥 표시, 클릭 가능 여부는 유용하지만 client 고유 상태다.
- 이런 기능이 공용 결과를 바꾸기 시작하면 전체 구조가 불안정해진다.

8. 최종 판단 기준

좋은 상태
- 상태줄은 거의 읽기 전용에 가깝다.
- popup은 공유된 해석 결과를 보여준다.
- jump와 jump-back은 이동과 복귀에 집중한다.
- collector는 공용 상태를 안정적으로 공급한다.
- 새 기능이 들어와도 "어느 층의 일인지"를 바로 설명할 수 있다.

나쁜 상태
- 상태줄이 스스로 해석하고 popup도 스스로 해석한다.
- client별 기능과 공용 기능이 같은 캐시와 산출물을 공유한다.
- helper가 제품 의미를 많이 알고 있다.
- 성능 문제를 고칠 때마다 개별 캐시만 계속 늘어난다.

메타 결론
- marmonitor의 성능 문제는 앞으로도 개별 기능이 아니라 경계 붕괴의 형태로 다시 나타날 가능성이 높다.
- 따라서 가장 중요한 것은 "더 빠른 구현"보다 "느려질 수 없는 위치에만 기능을 놓는 것"이다.
- 이 제품에서 지켜야 할 최소 규칙은 다음 다섯 가지다.
  - 실시간 경로는 얇게 유지한다.
  - 원본 상태와 파생 상태를 구분한다.
  - 해석은 공유하고 표현은 그 위에 얹는다.
  - 공용 상태와 client 고유 상태를 섞지 않는다.
  - benchmark는 구조를 대신하지 않고, 구조를 검증하는 데만 쓴다.
