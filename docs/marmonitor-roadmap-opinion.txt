marmonitor roadmap opinion

상태
- 지금은 기능 확장 단계보다 의미 정리와 안정화 단계에 더 가깝다.
- statusline 성능, collector, jump-back, idle right rail까지 핵심 축은 이미 usable 상태다.
- 따라서 다음 단계의 중심은 surface를 더 늘리는 것이 아니라, 현재 surface의 의미와 계약을 더 분명하게 만드는 것이다.

왜 지금은 확장보다 정리가 우선인가
- 상태줄은 이미 여러 역할을 맡고 있다.
  - 현재 대응해야 하는 것
  - 다시 투입 가능한 것
  - 점프와 복귀
  - summary popup 진입점
- 이 상태에서 새 surface를 계속 추가하면, 기능 수보다 규칙의 일관성이 먼저 무너지기 쉽다.
- 사용자 입장에서는 기능 수 자체보다 "언제 popup이고 언제 jump인지", "왜 지금 이 항목이 보이는지"가 더 중요하다.

현재 로드맵의 중심이 되어야 하는 것
1. 상태 의미 정합성
- `recent-complete / warm-idle / cold-idle`
- `⚠ = stalled + persistent unmatched`
- `transient unmatched`는 제외
- `persistent unmatched` 기본 grace period는 `120초`
- `risk`는 UI에 노출하지 않음
- idle rail이 의미하는 것이 무엇인지
- summary badge와 popup이 같은 의미를 가리키는지

2. 상호작용 계약 안정화
- summary click
- idle rail click
- detail item direct jump
- jump-back
- 이 상호작용들은 "언제 inspect이고 언제 act인지"가 일관되어야 한다.

3. collector 운영 품질
- restart 후 최소 전이 복원은 이미 들어갔다.
- 다음은 성능보다 설명 가능성이 중요하다.
  - stale / degraded 상태가 무엇인지
  - fallback이 왜 발생했는지
  - 현재 표시가 collector 기반인지 fallback 기반인지

4. 원칙 문서의 repo contract화
- 성능/구조 원칙은 더 이상 로컬 메모 수준에 머물면 안 된다.
- AGENTS와 제품 원칙 문서를 repo 기준선으로 올려야 이후 기능이 같은 판단 기준을 따른다.

지금 미루는 것이 맞는 것
1. 새 surface 추가
- dock / watch 확대
- popup 검색 / grouping 고도화
- richer daemon lifecycle
- direct file-read tmux path

2. full history 기반 상태 모델
- 현재는 최소 전이 기억으로 충분하다.
- 완전한 이벤트 로그는 지금 단계에서 비용이 더 크다.

3. 장식적 UI 확장
- 지금은 더 예쁜 것보다 더 설명 가능한 것이 우선이다.

추천 우선순위
1. 문서와 repo contract 정리
2. `⚠`와 idle 의미 정리
3. collector / fallback diagnostics 보강
4. 그 다음에만 새 기능 추가 검토

메타 결론
- 앞으로의 로드맵은 "무엇을 더 붙일까"보다 "지금 있는 것들의 의미와 계약을 얼마나 명확히 고정할까"를 중심에 두는 게 맞다.
- 현재 제품 상태에서는 그 순서가 가장 실용적이고, 장기적으로도 성능과 구조를 덜 망가뜨린다.
