점프백 표시 위치 조정 계획

목적
- 현재 `↩` jump-back 표시가 statusline 문자열 맨 뒤에 붙는다.
- 원하는 동작은 `↩`가 하단 번호 목록(`1`, `2`, `3` ...)보다 앞에 오는 것이다.
- 이 세션에서는 구현하지 않고, 영향 범위와 수정 계획만 정리한다.

현재 구조

1. `renderStatusline()` 책임
- 파일: `src/output/index.ts`
- `tmux-badges`일 때 아래 순서로 문자열을 만든다.
  - summary badge (`Cl`, `Cx`, `⚠`, `🤔`, `🔧`)
  - attention detail (`1 ... 2 ... 3 ...`)
- 구체적으로는:
  - `buildTmuxAttentionPills()`로 detail 문자열 생성
  - `buildTmuxBadgeBar(snapshot, focusText, style)`로 summary + detail 결합

2. jump-back 표시 책임
- 파일: `src/statusline-client.ts`
- 현재는 `runStatuslineClient()`에서 최종 문자열을 받은 뒤,
  - `appendJumpBackIndicator(output, hasAnchor)`
  - 형태로 맨 뒤에 `" ↩"`를 붙인다.
- 즉 jump-back 표시는 현재 statusline 레이아웃을 전혀 이해하지 못하는 후처리다.

문제 정의
- 사용성 관점에서 `↩`는 "현재 이 클라이언트에서 jump-back 가능"을 뜻한다.
- 따라서 detail 번호 목록보다 앞, 즉 "요약과 detail 사이의 얇은 상태 마커"로 보이는 편이 더 자연스럽다.
- 현재처럼 맨 끝에 붙으면:
  - 시선이 오른쪽 끝까지 가야 함
  - detail 항목과 관련 없는 부가 꼬리처럼 보임
  - 긴 상태줄에서는 존재를 놓치기 쉬움

목표 레이아웃

현재
- `Cl 1 Cx 8  ⚠ 4 🤔 3 🔧 1  1 ...  2 ...  3 ... ↩`

목표
- `Cl 1 Cx 8  ⚠ 4 🤔 3 🔧 1  ↩  1 ...  2 ...  3 ...`

핵심 원칙
- summary badge와 detail item의 의미는 바꾸지 않는다.
- jump-back 표시의 존재 조건도 바꾸지 않는다.
- `tmux-badges` 형식에만 적용한다.
- `compact`, `standard`, `extended`, `wezterm-pills`에는 영향 주지 않는다.

권장 구현 방향

1. 문자열 끝 덧붙이기 방식을 버린다
- 현재 `appendJumpBackIndicator(output, hasAnchor)`는 레이아웃 정보를 잃은 뒤 동작한다.
- 이 상태로는 원하는 위치로 옮기기 어렵다.

2. `tmux-badges` 전용 삽입 함수로 바꾼다
- `src/statusline-client.ts`에 아래 형태의 함수로 교체하는 것이 1차로 가장 단순하다.
  - 입력:
    - 최종 statusline 문자열
    - `hasAnchor`
  - 출력:
    - summary 영역 뒤, detail 영역 앞에 `↩`를 넣은 문자열

3. 삽입 규칙은 최소한으로 둔다
- statusline 문자열을 다시 파싱하는 대신, 현재 `buildTmuxBadgeBar()`의 조인 규칙을 이용한다.
- 현재 `tmux-badges`는 대략 `"summary  alerts  focus"`처럼 두 칸(`"  "`) 구분자를 쓴다.
- 1차 구현은 아래 규칙이면 충분하다.
  - `hasAnchor`가 아니면 그대로 반환
  - `focus`(detail) 구간이 있으면:
    - 마지막 구분자 앞에 `↩` 삽입
  - detail이 없으면:
    - 문자열 끝에 `↩`를 붙임

4. 더 나은 대안
- 장기적으로는 `buildTmuxBadgeBar()` 자체가 `jumpBackAvailable`을 인자로 받아 직접 배치하는 편이 더 명확하다.
- 다만 지금은 `output` 레이어를 건드리지 않고 `statusline client`에서만 끝내는 편이 변경 범위가 작다.

권장 단계

1단계
- `appendJumpBackIndicator()`를 대체하는 새 함수 추가
- 예시 이름:
  - `insertJumpBackIndicatorForTmuxBadges()`
- 위치:
  - `src/statusline-client.ts`

2단계
- `runStatuslineClient()`에서:
  - `format === "tmux-badges"`일 때만 새 삽입 함수 사용
  - 나머지 포맷은 기존 동작 유지

3단계
- 테스트 추가
- 기존 `statusline client` 테스트에 아래 케이스를 넣는다.

테스트 계획

1. detail이 있는 경우
- 입력:
  - `Cl 1 Cx 8  ⚠ 4  1 🤔Cx repo 3s  2 •Cx app 1m`
- 기대:
  - `Cl 1 Cx 8  ⚠ 4  ↩  1 🤔Cx repo 3s  2 •Cx app 1m`

2. detail이 없는 경우
- 입력:
  - `Cl 1 Cx 0`
- 기대:
  - `Cl 1 Cx 0 ↩`

3. anchor 없음
- 입력:
  - 위와 동일
- 기대:
  - 원본 그대로

4. tmux-badges 외 포맷
- `compact`, `standard`, `extended`는 기존과 동일

영향 범위

직접 변경 후보
- `src/statusline-client.ts`
- `tests/statusline-client.test.mjs`

간접 확인 필요
- collector artifact 내용은 바꾸지 않는다.
- 즉 `collector`가 저장한 statusline text는 여전히 anchor 없는 순수 출력이어야 한다.
- `↩`는 client별 상태이므로 collector가 아니라 client 쪽에서 붙는 현재 구조를 유지하는 것이 맞다.

이 방향이 타당한 이유
- jump-back 여부는 client별 상태다.
- collector snapshot이나 pre-rendered statusline text는 client별로 달라지지 않는다.
- 따라서 `↩`를 collector나 output core로 끌어내리기보다, client 후처리로 유지하는 편이 의미상 맞다.
- 다만 "문자열 맨 끝에 덧붙이기"만 layout-aware 형태로 개선하면 된다.

보류 사항
- `wezterm-pills`에서도 유사한 위치 규칙을 둘지는 별도 판단
- `↩`를 plain text가 아니라 click range나 별도 marker로 만들지는 1차 범위에서 제외

메타 결론
- 이 변경은 기능 추가가 아니라 레이아웃 조정이다.
- 가장 작은 수정은 `statusline-client.ts`에서 `tmux-badges` 문자열에 `↩`를 삽입하는 규칙만 추가하는 것이다.
- 구현 시에는 `output/index.ts`나 `collector`를 건드리지 않는 것이 안전하다.

추가 검토: jump-back 표시를 클릭 가능하게 만들지

판단
- 타당하다.
- 오히려 `↩`는 클릭 가능한 것이 UX상 더 자연스럽다.
- 이유:
  - 현재 번호 항목은 앞으로 가는 jump
  - `↩`는 뒤로 가는 jump-back
  - 두 동작이 같은 statusline surface에서 쌍을 이룬다.

주의할 점
- `↩`는 `pid:*`와 다르다.
- 특정 세션을 가리키지 않고, "현재 tmux client에 anchor가 있음"이라는 client 상태를 가리킨다.
- 따라서 `summary:*`나 `pid:*`와 같은 target 모델에 억지로 넣기보다, 별도 click target으로 다루는 편이 맞다.

권장 target 모델
- 현재:
  - `pid:<n>`
  - `summary:<target>`
- 확장:
  - `back`

예시 range
- `#[range=user|back]↩#[norange]`

권장 구현 방향

1. `↩`를 클릭 range로 감싼다
- 위치는 번호 목록 앞
- 예:
  - `Cl 1 Cx 8  ⚠ 4  #[range=user|back]↩#[norange]  1 ...  2 ...`

2. status-click helper가 `back`을 파싱하게 확장한다
- 새 타입:
  - `{ kind: "back" }`
- 기존:
  - `{ kind: "pid"; pid: number }`
  - `{ kind: "summary"; target: SummaryPopupTarget }`

3. `back` 클릭 시 실행 동작
- `marmonitor jump-back --client-tty <tty>`
- 즉 helper 내부에서 별도 tmux 로직을 다시 만들지 말고 기존 `jump-back` 명령을 재사용한다.

4. client-tty 전달은 필수로 유지
- `back`은 client-scoped anchor 기능이다.
- 따라서 현재 statusline이 이미 `--client-tty "#{client_tty}"`를 받는 구조를 그대로 이용해야 한다.

테스트 계획 추가

1. statusline client 문자열 테스트
- anchor가 있을 때:
  - `↩`가 번호 목록 앞에 들어가는지
  - 그리고 `#[range=user|back]...#[norange]`로 감싸는지

2. status click parse 테스트
- `back`이 `{ kind: "back" }`로 파싱되는지

3. click helper 실행 테스트
- `back` target이면 `jump-back` 경로를 타는지

왜 이 기능이 과하지 않은가
- 새 모델이긴 하지만 상태줄 surface 안에서 이미 존재하는 상호작용을 하나 더 여는 정도다.
- `pid`는 개별 세션 이동
- `summary`는 집계 popup
- `back`은 현재 client의 복귀
- 서로 의미가 명확히 구분된다.

메타 결론 추가
- `↩`를 단순 표시만 할지, 클릭 가능한 affordance로 확장할지는 2차로 보면 된다.
- 하지만 방향 자체는 타당하고, 현재 구조와도 잘 맞는다.
- 구현 시에는 `back`을 별도 status click target으로 도입하는 것이 가장 단순하고 정확하다.

`↩` 클릭을 같은 client 범위에서 안전하게 동작시키는 구체 설계

목표
- `↩` 클릭은 "현재 클릭한 statusline이 속한 tmux client"의 anchor만 사용해야 한다.
- 다른 탭, 다른 attach client, 다른 터미널 창의 anchor를 잘못 건드리면 안 된다.
- 즉 `back`은 전역 상태가 아니라 반드시 client-scoped 상태로 실행되어야 한다.

현재 전제
- 현재 jump-back 저장은 `clientId` 단위다.
- 현재 statusline 호출은 `--client-tty "#{client_tty}"`를 받고 있다.
- 현재 click helper도 `--client-tty "#{client_tty}"`를 받는다.
- 따라서 "클릭한 surface의 client"를 helper까지 넘기는 통로는 이미 있다.

핵심 설계

1. 표시 단계
- `statusline-client`가 `hasAnchor`를 판단한 뒤 `↩`를 삽입한다.
- 여기서 `↩`는 plain text가 아니라 아래처럼 click range로 감싼다.
  - `#[range=user|back]↩#[norange]`
- 중요:
  - `↩` 자체에는 client 정보나 anchor id를 encode하지 않는다.
  - client 문맥은 이미 tmux binding이 `#{client_tty}`를 넘기므로, range에는 `back`만 넣는 것이 더 단순하다.

2. click parsing 단계
- `status-click` helper는 아래 세 종류를 처리한다.
  - `pid:<n>`
  
구현 메모
- 2026-04-01 기준으로 이 계획은 반영했다.
- 현재 동작은 아래와 같다.
  - `tmux-badges`에서 anchor가 있으면 `↩`를 detail 번호 목록 앞에 넣는다.
  - `↩`는 `#[range=user|back]↩#[norange]`로 렌더된다.
  - `marmonitor-status-click back --client-tty <tty>`는 현재 client의 jump-back을 실행한다.
  - 로컬 tmux 바인딩은 `pid:*`, `sum:*`, `back`을 모두 helper로 넘긴다.
  - `summary:<target>`
  - `back`
- 새 타입:
  - `{ kind: "back" }`
- 이 타입은 별도의 session/pid 정보 없이 현재 client context만 요구한다.

3. 실행 단계
- `back`이 클릭되면 helper는 별도 tmux switch 로직을 새로 만들지 않는다.
- 반드시 기존 명령을 재사용한다.
  - `marmonitor jump-back --client-tty <tty>`
- 이유:
  - jump-back의 pane/window/session fallback 로직
  - anchor clear 규칙
  - invalid anchor 처리
  를 한 곳에서만 유지해야 한다.

4. client 전달 규칙
- `--client-tty`는 필수로 유지한다.
- helper는 항상 statusline을 그린 바로 그 client의 tty를 넘겨야 한다.
- 따라서 tmux binding은 아래 의미를 만족해야 한다.
  - `mouse_status_range` = 클릭한 item
  - `client_tty` = 클릭이 일어난 client
- 이 둘을 함께 helper로 넘기는 현재 구조가 맞다.

동작 시나리오

시나리오 A: 탭 A와 탭 B가 서로 다른 tmux client인 경우
- 탭 A에서 jump → anchor A 생성
- 탭 B에서 jump → anchor B 생성
- 탭 A의 `↩` 클릭 → `jump-back --client-tty A`
- 결과: anchor A만 사용
- 탭 B의 상태에는 영향 없음

시나리오 B: 탭 A에서 여러 번 jump한 경우
- 첫 jump 전 위치만 anchor A로 유지
- `↩` 클릭 → A의 origin으로 복귀
- 복귀 성공 시 anchor A clear

시나리오 C: anchor가 없는 client에서 `↩` 클릭
- 원칙적으로는 `↩`가 렌더되지 않아야 한다.
- 그래도 race나 stale render로 클릭이 들어오면 helper는 no-op 또는 실패 메시지로 끝난다.
- 다른 client anchor를 찾으러 가면 안 된다.

client-scoped 안전성 원칙

1. `back` target은 절대 global lookup을 하지 않는다
- 잘못된 예:
  - "아무 anchor나 있으면 back"
- 올바른 예:
  - "현재 client에 해당하는 anchor만 back"

2. lookup 순서는 명확해야 한다
- helper 입력:
  - `targetClient = client_tty`
- jump-back 명령 내부:
  - `resolveTmuxClientLocation({ targetClient })`
  - 여기서 현재 client를 식별
  - 그 client의 `clientId`에 해당하는 anchor만 읽는다

3. `client_tty`는 전달용, anchor key는 `clientId`
- `client_tty`는 클릭 surface 식별에 유용하다.
- 실제 anchor 저장/삭제는 `clientId`를 기준으로 유지하는 것이 맞다.
- 즉:
  - 표시/클릭 단계: `client_tty`
  - anchor storage 단계: `clientId`

4. fallback은 jump-back 내부에만 둔다
- helper는 back 클릭 시 "그냥 jump-back 명령 호출"
- pane/window/session fallback은 `jump-back` 책임
- click layer가 fallback을 중복 구현하면 두 경로가 쉽게 어긋난다.

권장 구현 단계

1단계: range 추가
- `statusline-client.ts`
- anchor가 있을 때 삽입하는 `↩`를
  - plain text
  - 또는 앞으로의 위치 조정 함수 안에서
  - `#[range=user|back]↩#[norange]`
  로 변경

2단계: helper target 확장
- `src/status-click.ts`
- `parseStatusClickTarget()`가 `back`을 파싱하도록 확장

3단계: helper 실행 분기 추가
- `{ kind: "back" }`이면
  - `jumpBackForClient({ targetClient: options.targetClient, insideTmux: true })`
  또는
  - 기존 CLI `jump-back` 명령 재사용
- 현재 코드베이스 기준으로는 직접 함수를 부르는 편이 테스트가 쉽고 비용이 적다.
- 다만 의미상 single source of truth는 `jumpBackForClient()`다.

4단계: tmux binding 유지
- binding은 이미 `client_tty`를 같이 넘긴다.
- 이 부분은 새 옵션을 추가할 필요가 없다.
- 다만 정규식은 `back`도 허용해야 한다.
  - 현재:
    - `pid:[0-9]+|summary:.+`
  - 확장:
    - `pid:[0-9]+|summary:.+|back`

테스트 구체화

1. parser
- `parseStatusClickTarget("back")`
- 기대:
  - `{ kind: "back" }`

2. statusline 문자열
- anchor 있음
- 기대:
  - `↩`가 `#[range=user|back]...#[norange]`로 출력됨

3. helper dispatch
- `back` target일 때:
  - pid lookup을 하지 않음
  - summary popup도 열지 않음
  - jump-back 경로만 탐

4. client isolation
- fake anchor 두 개:
  - client A
  - client B
- `--client-tty A`로 back 실행
- 기대:
  - A anchor만 사용
  - B anchor는 untouched

5. no-anchor path
- `back` 클릭인데 해당 client anchor 없음
- 기대:
  - no-op 또는 `found:false`
  - 다른 client anchor 사용 금지

유의점
- statusline text는 collector artifact를 재사용하더라도, `↩`는 client-specific 후처리이므로 collector에 저장하면 안 된다.
- `back` 클릭 가능성도 같은 이유로 collector가 아니라 client render 단계에서 range를 넣는 것이 맞다.
- 즉:
  - collector text = client-agnostic
  - final statusline string = client-aware

메타 결론
- `↩` 클릭 가능화는 타당하다.
- 구현 핵심은 "click target을 `back`으로 추가"가 아니라, "그 `back`을 반드시 현재 client 문맥으로만 해석"하는 것이다.
- 지금 구조는 이미 `client_tty` 전달선이 있어서, 이를 그대로 사용하면 cross-tab 오염 없이 구현할 수 있다.
